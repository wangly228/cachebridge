# 从缺块的重算成本到整段 p95

离线回放采用 cachebridge 的连续前缀语义。改变某个请求的首个缺块可能同时改变同波其他请求的入批形状、排队时间及 p95 排名。这里先固定不相关波的实测时间，对整个受影响波做反事实替换。样本为 4 个种子、每档 144 条 CPU 策略请求，每波并发 4。每一条原始请求、逐步调度、已测模型及 KV 搬运数据来自同机 Qwen3-4B BF16，GPU/CPU 为 36/64 块，每块 256 tokens。

| 淘汰后重访比例 | 未完整恢复请求 / 重访 | 受影响波 / 同波请求 | 额外重算 tokens | 实测 p95（ms） | 完美恢复的整波参考（ms） | 改善的乐观上限 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 0% | 0 / 0 | 0 / 0 | 0 | 918.02 | 918.02 | 0% |
| 33⅓% | 27 / 48 | 8 / 32 | 40,960 | 904.65 | 897.70 | 0.77% |
| 66⅔% | 33 / 96 | 12 / 48 | 50,176 | 913.92 | 884.44 | 3.23% |

“整波参考”取六种子正式归档中混合淘汰重放的 12 个满恢复波，按相同 FIFO 位置与前缀长度布局计算每位置耗时中位数。这些参考波都从 CPU 恢复 24 个块，在一个 prefill 步中处理四条各 128 tokens 的尾查询。把有缺口的波替换为参考，其他波保留实测值，再排序计算整段 p95。独立求乐观界时，更进一步把整波四个请求的时间都压成 0 ms，两种替换在三档产生相同 p95。这个界限以其余波完全不变为前提。改变首次写入预算、块淘汰或批形状后，需要真机计入其他波的变化。最高重访档原 p95 由两个新前缀请求支撑；未完整重访波中也有请求比这两条更慢，其位置会在反事实排序中改变。[逐请求结果](boundary_requests.jsonl) · [插值支撑与区间](summary.json)

## 3090 的重算、写入与恢复成本

从原有 3090 单请求配对校准中分别选 4 对 1024-token 前缀和 4 对 2048-token 前缀，各留 128-token 尾查询。对每一对，在重算 TTFT 中扣除实测同步 D2H，在恢复 TTFT 中扣除实测 H2D，两者之差估计节省的非搬运经过时间（含前向和主机开销）。表中三列均为配对样本的中位数。对只缺一部分的前缀，按未恢复 token 比例线性分配同长度的校准成本，这一步属于估计。

| 重算的完整前缀长度 | 非搬运差（ms） | H2D（ms） | 一次同步 D2H（ms） |
| ---: | ---: | ---: | ---: |
| 1,024 | 120.63 | 15.29 | 15.61 |
| 2,048 | 259.80 | 31.23 | 30.78 |

在 66⅔% 档，补齐 196 个块，按上述孤立请求样本估计累计非搬运时间差 6,217 ms、额外 H2D 760 ms。若每个额外恢复块都需要一次额外同步写入，对应 758 ms，这是另一种假设下的写入服务量。实际在线策略可能写入其他最终不复用的块，也可能重复使用早先的同一写入。后台 D2H 与前向可重叠，批处理也改变计算形状，因此这些累计量不能直接换算为整段 p95。33⅓% 档对应 160 个块、5,075 ms、620 ms 和 618 ms。每条请求的估计与校准原值保存在 JSON 中。[单请求 1024 校准](../20261118_queue_c_calibration/pairs.jsonl) · [单请求 2048 校准](../20261118_stage2_c_calibration/pairs.jsonl) · [可复算汇总](summary.json)

## 冻结主负载的尾部

在原六种子主对照中，两种负载的 48 条淘汰重放均完整恢复。将发生写入的冷波换成同轮原生 A 的实际 TTFT，逐请求匹配输入、相同初始命中和相同 prefill 调度形状，其他波保留 overlap32 实测值。混合负载整段 p95 从 908.70 变为 893.31 ms（−1.69%），全长从 1202.76 变为 1175.66 ms（−2.25%）。替换值是同轮其他臂的观测，包含测量波动。不同写入策略能否达到这一变化需要实测。混合有 12 个冷填充波、12 个首波干扰发生写入，第二波干扰始终零写入。全长只有 12 个冷填充波写入。[逐请求配对](formal_requests.jsonl)

混合整段 p95 的两条支撑请求均在冷填充波的第 5 个 prefill 步首次吐出 token，分别已经历了 906.91 和 908.78 ms 的 Runner 调用。全长的两条支撑请求均等到第 8 步，Runner 累计为 1200.20 和 1201.42 ms。混合 12 个冷填充波共执行 60 步，实际处理 79,872 个 query tokens，按每步 2,048 的上限有 43,008 个空余 token 位置。若可连续填满预算，步数的理论下界为 48。全长 12 个冷填充波为 96 步、104,448 个 query tokens、92,160 个空余位置，步数下界为 60。对应无复用干扰波也有相同的步数和空余位置总数（每 12 波）。混合和全长冷填充中，各有 12 和 48 个 128-token 的小步，Runner 中位耗时 49.02 和 49.28 ms。部分填满额外请求会改变 attention 形状和单位 token 成本，空余位置与可省时长不能等同。这些观测支持在相同 FIFO、预算和容量下，单独筛查让下一个冷请求进入剩余预算的候选。[实际步数、每步耗时与 p95 支撑请求](summary.json)
