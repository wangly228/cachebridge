# cachebridge 项目进度

cachebridge 在 nano-vLLM 上实现了有容量上限的 CPU 前缀 KV 缓存。实验使用单张 RTX 3090 24 GB、Qwen3-4B BF16，主指标为从请求入队到首个输出 token 的 p95 延迟。

## 2026-11-23 CPU 历史 KV 量化验收

本轮从 `main` 的 `e69c824279c0da2b10f5078d0174b80f0fff03d5` 和上轮冷合批未提交的工作树接手。Qwen3-4B 权重和活跃 GPU KV 为 BF16；`cpu_prefix_cache_format="int4"` 在保存时按 32 个坐标打包，CPU 页和 PCIe 搬运都用压缩格式，恢复时解至独占 BF16 页。以往阶段的结果与开关继续保留。54 项测试通过。[路径、参考提交与保护条件](INT4_PREFIX_CACHE.md) · [测试日志](../results/20261123_int4_final_tests.txt)

单卡 3090、6 个独立种子、并发 4、每请求 16 个输出 tokens，三臂共 1,224 条正式请求。同为 64 slots 时每块实际节省 71.875%，混合重放 p95 下降 34.46%（配对 95% 区间 −40.10% 至 −31.41%），混合整段下降 0.76%。同为 648 MiB CPU 页池时，两种格式在容量轨迹分别容纳 BF16 18 块和 INT4 64 块，重访完整恢复由 24/96 增至 96/96，p95 由 562.47 降至 97.14 ms；容量整段变化 −1.01%，区间跨零。[冻结判据](INT4_PREFIX_PROTOCOL.md) · [同轮汇总](../results/20261123_int4_prefix_formal/summary.json)

独立正式质量对照覆盖 2048、8192、12288-token 历史。64-token 输出窗口下，单跳正确数为 BF16 16/18、INT4 18/18，两跳为 13/18、7/18，整体质量线未过。将全部 13 道失分题复查至最多 192 个输出 tokens，六道原本仅 INT4 失分的两跳题均给出正确码，完整回答变长；另有 3 条 INT4 回答到 EOS 仍取错码。CPU 容量或搬运受限、且能容许措辞变化的单跳重放可显式启用；紧回答预算的多跳任务与精确复现保留 BF16。推广到新任务时，下一步是用其真实回答上限和长上下文样本复核正确答案丢失数，再核对含冷填充的整段 p95。[逐题质量](../results/20261123_int4_quality_formal/summary.json) · [扩窗诊断](../results/20261123_int4_answer_length/summary.json)

## 2026-11-23 基于回放的优化

本轮在上轮未提交的 overlap 32 工作树上继续，保留原开关和旧实验。回放与本机成本分析表明，66⅔% 重访档的 33 个首缺块中有 27 个首次未写、6 个曾写入后被淘汰。原正式整段 p95 的支撑请求来自冷填充，淘汰重放已完整恢复。保留的改动是用 FIFO 下一条全冷请求补足当前 prefill 步，不改变 CPU 缓存准入与物理容量。候选为可选配置 `cpu_prefix_pack_cold=True`。它降低队尾等待，也会拉高队首等待，混合整段 p50 从 326.72 升至 506.91 ms。独立四种子实测 0%、33⅓%、66⅔% 三档重访，整段 p95 分别比 overlap 32 低 5.86%、6.76%、7.96%，三个配对区间均低于零。改变 BF16 执行形状后，部分 greedy 序列与旧调度不同。[同形状正确性与 FIFO 权衡](STAGE2_COLD_PACK.md#队首等待与数值差异) · [最新三档重访比例](STAGE2_COLD_PACK.md#重访比例边界)

## 2026-11-23 本地验收

公开工作区从干净的 `main`、HEAD `e69c824` 开始，使用已安装环境加载公开源码和原模型。种子 1803 周期 0、1804 周期 1 上，关闭诊断时，相同 32 块配置重复的合并 p95 相差 5.34 ms，32 与 36 块相差 0.99 ms。对比原生 A，32 块冷填充 p95 多出 73.79 ms，每波同步写入平均耗时 77.51 ms。80 次诊断写入后均有下一步前向计算窗口。[分段计时与两波复测](STAGE2_COLD_FILL_PROBE.md)

本轮只验证了一个候选。保留按复用写入、32 块首次写入额度和双缓冲，在需要该策略的 `LLM` 上显式设置 `cpu_prefix_transfer_mode="overlap"`。后台同时最多写一批。调度器持有 GPU 源块与 CPU slot，传输完成后才发布 CPU 命中。默认模式为 `sync`。6 个独立种子、两种访问顺序、共 1,296 条正式请求，864 条 CPU 策略请求通过同形状原生 greedy 对照。48 条先淘汰再首次重放的候选请求全部恢复。全长整段比同步版低 5.12%，无复用和淘汰重放分别高 1.17% 和 0.10%。[原始逐请求记录和汇总](../results/20261123_overlap_formal/summary.json)

## 淘汰后重访比例与整段 p95

单张 3090、Qwen3-4B BF16、CUDA Graph 开启。每个独立周期从空 GPU/CPU 索引开始，连续执行 9 波，每波并发 4。GPU 实际 36 块，CPU 容量 64 块，每块 256 tokens。每波各两条 1024、2048-token 前缀，另加 128 个输入 tokens，greedy 输出 128 个 tokens。前三波输入不同，后六波按档位提供新前缀或重访至少间隔两波的历史前缀。比例分母是整段全部请求。4 个种子，每档每臂 144 条，合计 864 条正式请求。逐请求核对两臂初始 GPU 命中均为 0。下表每个 p95 均由该档完整请求序列直接计算，其中包括冷填充和所有干扰波的请求。TTFT 从入队计至首个真实输出 token，整段墙钟覆盖全部搬运与等待。区间按完整种子配对重采样 4,000 次。[冻结输入与设计](../results/20261123_revisit_boundary/design.json) · [时间戳及搬运量](../results/20261123_revisit_boundary/requests.jsonl)
